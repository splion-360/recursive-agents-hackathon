Hackathon research brief · 16 October 2026

Can a harness live in memory instead of weights?

A multimodal experiment inspired by Harness-Zero: let a strong reviewer repair a smaller student’s actions, distill those repairs into MemMachine, then remove the reviewer and measure whether retrieved behaviors preserve the gain.

Recommendation: build the memory-distilled system first and treat fine-tuning as an optional stretch. The core claim is stronger for this venue if a fresh student improves on held-out ChartQA and MathVista tasks using reusable memories, with the reviewer absent at evaluation time.

Decision brief

Novel enough to stand out. Technical enough if the controls are rigorous.

The idea is not “RAG over old answers.” It is a closed-loop transfer system with a privileged reviewer, structured behavior extraction, retrieval policy, contamination controls, and a held-out ablation study.

Novelty · strong

The transfer medium changes

The paper puts harness-induced behavior into model parameters. This project asks whether the same behavior can remain external, portable, inspectable, and revisable inside long-term memory. The modality also changes from the paper’s tool environments to visual reasoning.

Technical defense

The system must prove transfer, not retrieval

Store no final benchmark answers in semantic memory. Retrieve procedural behaviors only. Evaluate on disjoint tasks, keep the reviewer off, and include shuffled-memory and raw-trajectory controls. Those choices separate genuine behavior transfer from answer leakage.

01 · Paper findings

Harness-Zero turns a strong harness into supervision.

The September 2026 preprint studies how to preserve the benefits of specialized agent scaffolding after that scaffolding is removed.

STUDENT

The task-solving language model operating under a fixed, minimal target harness. It does the work. It does not design the harness.

h

The minimal target harness used for training trajectories and final deployment. In the paper, it is a fixed mini-SWE-agent configuration with one Bash execution tool.

h*

The optimized, domain-specific harness whose induced behaviors should be transferred. It may expose different tools and information from the target harness.

REVIEWER

The “agent-as-harness.” Guided by the optimized harness, it intercepts the student’s proposed response before execution, passes sound actions through, and otherwise supplies a minimal correction in the student’s action space.

DISTILL

The accepted and corrected trajectories become supervised fine-tuning data. At deployment, the optimized harness, private guidance, and reviewer are removed.

Base model + minimal harness
23.3%
Base model + optimized harness

Distilled model + minimal harness
44.3%

Macro-average reported across SpreadsheetBench Verified, AppWorld, and USPTO Retrosynthesis. The 44.3% result is for Qwen3.5-9B after fine-tuning on reviewed trajectories.

Inference finding

Agent beats code

Without training, agent-as-harness averaged 81.1% across six benchmark-model settings, versus 78.1% for the optimized code harness.

Behavior finding

82.3% recovered

The distilled student recovered an average 82.3% of 28 behaviors induced by the optimized harness but absent from the base model.

Limitation

Collection is slower

The reviewer must be capable, and one reported collection setting incurred roughly 2.4× latency. Deep domain knowledge transferred less completely than procedural behavior.

02 · Hackathon proposal

Memory Distillation: a living harness without weight updates

A small multimodal student learns reusable visual-reasoning procedures from a stronger reviewer. Instead of LoRA or SFT, reviewed experience becomes episodic memory and then compact behavior cards in MemMachine.

Research hypothesis

A student with the minimal harness plus retrieved behavior memory will outperform the same student without memory on held-out visual reasoning tasks, while using fewer model calls and less latency than online reviewer guidance.

Falsifiable outcome

If memory-only accuracy does not exceed the minimal baseline, or if shuffled memories perform just as well, the hypothesis fails. The result is still informative about whether procedural harness behavior can live outside weights.

Core experiment Collect reviewed trajectories on benchmark-provided development items. Consolidate only general procedures. Freeze the memory snapshot. On disjoint evaluation items, disable the reviewer and compare minimal harness, optimized harness, reviewer-guided, and memory-distilled conditions.
03 · Build decomposition

Nine components, each with one defensible job

The technology choices favor measurable behavior and a complete system over speculative training infrastructure. Exact Crusoe API identifiers should be confirmed against the hackathon account before implementation.

01

Published task suite

Purpose

Supply visually rich tasks with known answers and official evaluation logic.

Why

Avoid spending the event inventing an environment or defending hand-curated examples.

Technology

ChartQA human-authored split and MathVista testmini, loaded with Hugging Face Datasets and fixed manifests.

02

Minimal harness h

Purpose

Define the student’s small, stable action space for every condition.

Why

The reviewer must correct actions the student can actually produce; deployment must stay constant.

Technology

Fixed system prompt plus four typed actions: inspect_image, crop, run_python, and final_answer.

03

Optimized reference harness h*

Purpose

Encode the stronger visual-reasoning procedure that guides review.

Why

Creates a real behavior gap to transfer, rather than asking one model to self-critique vaguely.

Technology

Planner, region inspection, legend/axis protocol, OCR fallback, Python arithmetic, answer normalization, and final verification rubric.

04

Student agent

Purpose

Solve benchmark items under the minimal harness and expose weaknesses the reviewer can repair.

Why

A smaller model leaves headroom for observable transfer and keeps repeated evaluation affordable.

Technology

Planned: Gemma 3 12B IT on Crusoe Managed Inference. Use low temperature and structured JSON actions; confirm the venue’s exact multimodal endpoint ID.

05

Reviewer agent at the response boundary

Purpose

Intercept each student action before execution and emit PASS or the smallest valid replacement.

Why

This is the paper’s key translation step: privileged guidance becomes supervision in the student’s own action space.

Technology

Planned: Nemotron 3.5 Super VL 120B on Crusoe serverless inference, with the reference-harness rubric and access to the image plus trace.

06

Consolidator agent

Purpose

Turn repeated corrections into short behavior cards and merge duplicates or contradictions.

Why

Raw trajectories are long and instance-specific. The student needs compact, reusable procedures.

Technology

Qwen3 235B A22B Instruct on Crusoe; JSON schema with trigger, procedure, verification, support count, failure modes, provenance IDs, and confidence.

07

MemMachine memory layer

Purpose

Persist reviewed episodes and serve distilled behaviors across runs and model sessions.

Why

Memory is the proposed distillation target, not a log attached after the fact.

Technology

MemMachine Python SDK or REST API. Episodic memory stores reviewed traces; semantic/profile memory stores behavior cards. Scope by benchmark, role, and run using group_id, agent_id, and metadata.

08

Evaluator and contamination guard

Purpose

Score answers, measure system cost, and prove evaluation items never enter memory.

Why

Without split isolation, improvement could be memorization rather than behavioral transfer.

Technology

Official benchmark answer normalization/evaluation code, immutable PID manifests, answer stripping before consolidation, SHA-256 task guards, and JSONL run telemetry.

09

Experiment dashboard

Purpose

Make corrections, memories, retrievals, and metric deltas visible in one live story.

Why

The visual proof must show the mechanism, not only a final bar chart.

Technology

Streamlit + Plotly: image/question panel, student-versus-reviewer action diff, memory write/read feed, behavior graph, accuracy, latency, and token charts.

04 · Task suite

Use the benchmark as the environment.

Every task comes from a published dataset. Selection is deterministic, split-aware, and reproducible. No puzzle or answer is authored during the hackathon.

ChartQA

Read and reason over real charts

Questions require locating values, resolving legends and axes, comparing series, and performing arithmetic. The dataset includes chart images, human-authored and machine-generated questions, annotations, and underlying tables.

Planned slice

Human-authored training items for collection; a disjoint human-authored validation/test manifest for evaluation. Start with 100 collection and 50 evaluation items.

Scoring

Use the repository’s official answer normalization and relaxed accuracy implementation.

MathVista testmini

Mathematical reasoning in visual contexts

The 1,000-item testmini split spans multiple-choice and free-form tasks involving diagrams, plots, geometry, tables, and everyday images. Public labels make local evaluation possible.

Planned slice

Create collection and held-out manifests by deterministic PID hash, stratified by task and answer type. Start with 100 collection and 50 evaluation items.

Scoring

Use MathVista’s official response extraction and answer-normalization logic.

MathVista dataset
Fairness rule Retrieval queries may contain the new task’s modality, reasoning type, and requested operation, but never its ground-truth answer. Behavior cards may reference source trajectory IDs for provenance, but their text must not retain chart values, image IDs, options, or final answers.
05 · System design

The correction loop becomes the product.

Collection and deployment share the same minimal student harness. Only collection includes the reviewer; only deployment consumes the frozen memory snapshot without reviewer help.

FROZEN BEHAVIOR SNAPSHOT → RETRIEVAL → FRESH STUDENT RUN · REVIEWER OFF

Collection mode

Reviewer on. Every action is checked. The system logs accepted and replaced actions, execution observations, task result, and correction reason. Consolidation runs after a batch, not after every item, to expose recurring behavior.

Evaluation mode

Reviewer off. Memory writes off. The frozen memory snapshot is read-only. The student receives top-k behavior cards and may optionally request one episodic example if confidence is low.

07 · Theme alignment

A recursive team that improves its own operating procedure

The proposal should be pitched as a team whose work product is a better future harness, not as several LLM calls placed in sequence.

Recursive agency

A reviewer agent supervises a student agent; a consolidator studies that supervision and rewrites it into policy-like memory for the next student.

Self-check and recovery

Every proposed action crosses a response boundary before execution. Failures become structured evidence rather than discarded logs.

Long-running autonomy

Collection, consolidation, and evaluation can proceed by manifest while the team accumulates and refines its shared memory.

Delegation

The student solves, tools inspect and calculate, the reviewer enforces quality, the consolidator abstracts, and the evaluator remains independent.

Shared memory

MemMachine is the coordination substrate across roles and sessions, not a secondary analytics store.

Measured improvement

The team earns its complexity only if held-out accuracy rises and reviewer-free deployment reduces latency or token cost.

09 · Evaluation plan

Four bars tell the story. Two ablations make it credible.

Minimal baseline

Student + minimal harness. No reviewer, no memory. Establishes the floor.

Optimized harness attached

Student uses the stronger fixed procedure and tools directly. Establishes what is available to transfer.

Reviewer-guided

Student stays in the minimal action space while the reviewer intercepts every action. Establishes the online ceiling and collection cost.

Memory-distilled

Fresh student, minimal harness, frozen MemMachine snapshot, reviewer off. This is the primary result.

Raw-trajectory retrieval

Retrieve full episodes instead of behavior cards. Tests whether consolidation adds value beyond ordinary example retrieval.

Shuffled-memory control

Inject equally sized but irrelevant behavior cards. Tests whether gains come from relevant procedure rather than extra context.

gap recovery = (accuracymemory − accuracyminimal) ÷ (accuracyreviewer − accuracyminimal)

Capability

  • Task accuracy overall and by benchmark
  • Gap recovery
  • Accuracy after helpful, neutral, and harmful retrieval
  • Behavior coverage by error category

Efficiency

  • End-to-end p50 and p95 latency
  • Input/output tokens per solved item
  • Model calls and tool calls
  • Reviewer collection overhead

Memory quality

  • Retrieval hit rate at k
  • Correction-to-behavior compression ratio
  • Duplicate and contradiction rate
  • Held-out answer leakage: target 0
Decision threshold A compelling result is not necessarily parity with online review. The practical win is statistically visible accuracy gain over the minimal baseline, clearly relevant retrievals, and lower latency or token use than calling the reviewer on every action.

11 · Risks

Make every failure diagnosable by noon Saturday.

No capability gap

Symptom: student already solves nearly everything.

Mitigation: use harder benchmark strata, smaller student, stricter minimal tools, and preserve the same evaluation manifest.

Answer leakage

Symptom: memory wins suspiciously on near-duplicates.

Mitigation: answer stripping, PID/hash guard, disjoint splits, lexical overlap audit, and shuffled-memory control.

Bad retrieval

Symptom: irrelevant cards increase context and lower accuracy.

Mitigation: metadata filter by benchmark/task type, hybrid search, small top-k, score threshold, and no-memory fallback.

Weak reviewer

Symptom: corrections do not improve execution.

Mitigation: test on 20 labeled items first, expose image and full state, require tool-valid JSON, and compare reviewer-corrected action outcomes.

Over-consolidation

Symptom: generic advice replaces precise procedures.

Mitigation: require repeated support, preserve trigger and verification fields, and keep provenance links to episodes.

Integration drag

Symptom: MemMachine or Crusoe setup consumes Friday.

Mitigation: prove one write/search and one multimodal call before orchestration; keep thin adapters and a JSONL mirror for debugging only.

Demo network risk

Symptom: live calls stall on stage.

Mitigation: cache one verified replay, precompute all aggregate results, and mark replay mode visibly rather than pretending it is live.
